# Whistle v1 — Manual QA checklist

Generated by U12 (TECH-SPEC §2a Definition of done, point 4). This is the
compiled list of every verification that needs a human at the keyboard,
real hardware, a live network condition, or a TCC permission dialog —
things the automated suites (63 backend vitest tests, 36 whistle-core
`swift test` tests, 83 `xcodebuild test` app-target tests, all green as of
this writing) cannot exercise unattended.

**Host:** macOS 15.7.3, Apple Silicon, Xcode 26.3. Single-OS walk only —
macOS 14 and macOS 26 hardware are not available here, so anything that
requires either is called out explicitly and left unchecked.

Work top to bottom. Each item is one action → one expected outcome. Check
the box when you've personally observed the expected outcome.

## First-run experience

- [ ] **Action:** Create a fresh macOS user account (or fully reset
  onboarding state — delete the app's UserDefaults domain
  `build.conductor.whistle.app` and any GRDB store under Application
  Support), install Whistle, and time yourself from first launch through
  a completed real capture reaching *Ready*.
  **Expected outcome:** under 5 minutes total (PRD activation success
  metric). Record the actual time.
- [ ] **Action:** Walk the wizard step order exactly: sign in → combined
  mic+speech permission screen → API key + validation → project step →
  guided test capture → screenshot upsell.
  **Expected outcome:** project step is skipped/auto-selected if the
  account has exactly one Conductor project, shown as a picker otherwise;
  screen-recording is never presented as a blocking step before the first
  capture, only as a post-capture upsell.
- [ ] **Action:** Deny mic, deny speech, and leave screen-recording
  unresolved, all on the combined permission screen; continue through the
  wizard.
  **Expected outcome:** wizard proceeds with degraded-mode messaging
  (never hard-blocks on these three); only sign-in and API key validation
  are hard gates.
- [ ] **Action:** Kill the app mid-wizard (after the permission step,
  before test-capture) and relaunch.
  **Expected outcome:** wizard resumes at the correct step; earlier
  permission grants are not lost or re-prompted.
- [ ] **Action:** Grant screen-recording via the post-first-capture
  upsell, which forces an app relaunch.
  **Expected outcome:** onboarding-completion state and wizard progress
  survive the relaunch; the app doesn't re-show completed steps.

## Capture & transcription

- [ ] **Action:** Trigger capture via hotkey (⌥⇧W) and via left-click on
  the menu bar icon, watching Console.app for the `onTimingMeasured` log
  line (`Whistle: capture trigger->interactive took NNNms`,
  `CapturePanelController.swift`).
  **Expected outcome:** panel visible and interactive in under 300 ms
  (PRD F1/TECH-SPEC §4.2 target). Record the observed ms for both trigger
  methods.
- [ ] **Action:** With another app frontmost (e.g. a text editor with
  focus in a document), trigger capture, type a few characters into the
  panel's notes field, then dismiss the panel (submit or Esc).
  **Expected outcome:** typed characters land in the capture panel, not
  in the previously-frontmost app's document; after dismiss, focus
  returns correctly and the previously-frontmost app is still usable
  without needing to click back into it (this is the "capture never
  yanks you out of your app" contract, TECH-SPEC §4.1).
- [ ] **Action:** Flip the panel-mode debug flag
  (`UserDefaults` key `WhistleCapturePanelMode`, values `nonActivating`
  (default) / `activating`) and repeat the trigger + typing test above
  under `activating` mode.
  **Expected outcome:** compare feel between the two modes (does
  `activating` visibly steal focus from / deactivate the previous app on
  show, and does it cleanly restore it on dismiss?). **Pick the winner**
  and record the decision here:
  Decision: ______________________ (default ships as `nonActivating`
  unless this walk determines otherwise — update
  `CapturePanelController.CapturePanelMode.current(defaults:)`'s fallback
  and this line if the decision changes).
- [ ] **Action:** Deny mic permission (System Settings → Privacy →
  Microphone → toggle Whistle off), then trigger a capture.
  **Expected outcome:** panel opens in type-only mode with an inline
  "enable mic" link to System Settings; no crash.
- [ ] **Action:** Deny Speech Recognition permission (System Settings →
  Privacy → Speech Recognition), independent of mic, then trigger a
  capture.
  **Expected outcome:** panel degrades to type-only / prompts to enable
  speech recognition; no crash.
- [ ] **Action:** Deny Screen Recording permission (or never grant it),
  then trigger a capture.
  **Expected outcome:** capture proceeds without a screenshot; the
  thumbnail slot shows an "enable in Settings" affordance instead of a
  broken image.
- [ ] **Action:** On a machine/account where on-device speech has no
  downloaded model (fresh install, dictation never enabled): trigger a
  capture.
  **Expected outcome:** prompt to enable/download the dictation model via
  System Settings → Keyboard → Dictation, with type-only fallback in the
  meantime.
- [ ] **Action:** Dictate continuously for 6+ minutes in a single capture
  session (real mic, real speech, on real macOS 14 or macOS 15/26
  hardware), watching for the soft-cap hint past 5 minutes.
  **Expected outcome:** task-cycling/segment-stitching (TECH-SPEC §4.1b)
  produces one continuous, correctly-ordered transcript with no dropped
  join-space, no duplicated words, and no gap at segment boundaries; a
  gentle UI hint appears past the 5-minute soft cap but the transcript
  keeps accumulating and the capture still submits successfully.
- [ ] **Action (macOS 26 only):** repeat the 6-minute dictation test on
  macOS 26+ hardware where `SpeechAnalyzerTranscriber` is selected at
  runtime (`#available` factory pick).
  **Expected outcome:** same stitching correctness as the legacy path.
  **Status:** partially run 2026-07-27 on macOS 26.5.2 (M4 Pro). The
  first-ever real execution of this path crashed the shipped 1.0.9 app —
  an uncatchable Speech-framework precondition, "Audio sample data must
  be 16-bit signed integers", from feeding native Float32 tap buffers to
  `AnalyzerInput` unconverted (fixed in 1.0.10 via `AudioBufferConverter`
  + `AssetInventory.reserve`; see `SpeechAnalyzerTranscriber.swift`
  header). Post-fix, a live capture ran 35+ s on-device with mic input
  flowing: no SIGTRAP, and neither the 16-bit-precondition nor the
  "unallocated locales" message in the unified log. Still to do by a
  human: the full 6-minute real-speech dictation pass checking transcript
  stitching quality.
- [ ] **Action (macOS 14 — not available on this host):** repeat capture
  + dictation smoke tests on real macOS 14 hardware.
  **Expected outcome:** `LegacySpeechTranscriber` (`SFSpeechRecognizer`)
  behaves identically to the macOS 15 behavior observed above.
  **Status:** not run — no macOS 14 hardware available in this
  environment.
- [ ] **Action:** Go offline (Wi-Fi off) and submit a capture.
  **Expected outcome:** capture queues locally with status *Waiting for
  network*; no error dialog. Reconnect Wi-Fi.
  **Expected outcome:** queued capture auto-syncs without user action.
- [ ] **Action:** Submit a completely empty capture (no speech, no typed
  text, screenshot removed).
  **Expected outcome:** Submit button/action is disabled.
- [ ] **Action:** Remove the auto-captured screenshot, leave transcript
  and notes empty, and submit.
  **Expected outcome:** submit is allowed; the capture's `notes` field is
  auto-populated client-side with "screenshot-only capture".
- [ ] **Action:** Open the capture panel, then press the hotkey again
  while it's already open.
  **Expected outcome:** existing panel is focused; no second screenshot
  is taken (no visible flash/re-capture).
- [ ] **Action:** Press Esc with content in the panel (transcript, notes,
  or screenshot present).
  **Expected outcome:** a confirm step appears before the panel closes
  (content isn't silently discarded).
- [ ] **Action:** Press Esc with an empty panel.
  **Expected outcome:** panel closes immediately, no confirm.

## Pipeline & history

- [ ] **Action:** With a valid Conductor API key and reachable network,
  submit a real capture and watch the History window status chip live,
  end to end, without refreshing/relaunching the app.
  **Expected outcome (live end-to-end walk, depends on prerequisite #1
  above being resolved):** status visibly progresses *Queued* → *Creating
  workspace* → *Agent working* → *Ready (+N questions)*; exactly one
  macOS notification fires for the *Ready* transition (not zero, not
  more than one); clicking the notification opens the Conductor deep
  link and the History row's `openedAt` gets patched.
- [ ] **Action:** Click a *Ready* notification (from the item above, or
  any subsequent one).
  **Expected outcome:** the correct workspace deep link opens in the
  browser/Conductor app; the corresponding History row's `openedAt` is
  set on click, the row visually de-emphasizes, and the menu-bar
  ready-indicator dot count decrements. Clicking the same notification
  path again (e.g. re-opening the same row from History) does not
  re-patch `openedAt` or re-decrement the indicator.
- [ ] **Action:** Enter an invalid/revoked Conductor API key in Settings
  and submit a capture.
  **Expected outcome:** pipeline fails with *Auth error*; the failure
  notification deep-links to Settings → API key, not to a workspace.
- [ ] **Action:** Submit a capture against a Conductor project with a
  broken repo/setup (or reuse the "ttl" project before its credentials
  are fixed, per item #1 — this is a live demonstration of the row
  "Conductor workspace creation fails").
  **Expected outcome:** status shows *Failed* with the `errorMessage`
  from the status endpoint; a Retry affordance is present and calling it
  (`captures.retry`) does not create a second workspace.
- [ ] **Action (requires letting a real workspace run for the full
  window, or manipulating server timestamps in a scratch environment):**
  observe a capture whose agent never confirms completion within 60
  minutes.
  **Expected outcome:** status shows *Sent — agent status unknown*
  (`readyUnverified`) with the workspace deep link; no false "Ready"
  notification fires.
- [ ] **Action:** Force a pipeline stall (e.g. kill the Convex dev
  deployment mid-flight on a capture stuck in `sending`, or otherwise
  induce a 90-minute stranded state).
  **Expected outcome:** the watchdog marks it *Failed (stalled)*, a
  notification fires, and Retry is available.
- [ ] **Action:** Put the Mac to sleep (clamshell/lid-close) immediately
  after submitting a capture, before the pipeline has reached a terminal
  state, then wake it later.
  **Expected outcome:** the pipeline continues server-side while asleep
  (Convex actions are server-side, not on-device) — on wake, the History
  row reflects whatever state the server reached in the meantime, with no
  stuck/orphaned local state and no duplicate workspace.
- [ ] **Action:** From a History row for a completed capture, choose
  "Duplicate as new capture" on a row that is **local-only** (never
  synced to the server).
  **Expected outcome:** a new capture panel opens pre-filled with the
  original transcript, notes, and screenshot, with the project picker
  focused and a freshly minted `clientId`.
- [ ] **Action:** Repeat "Duplicate as new capture" on a row that **is
  server-synced** (has a `serverRecord`).
  **Expected outcome:** transcript/notes/project pre-fill correctly, but
  the screenshot is *not* re-hydrated into the new capture — this is a
  documented limitation (`WhistleApp.resolveScreenshotData`: screenshot
  re-fetch over HTTP for server-synced rows isn't implemented in v1).
  Confirm this is the observed (expected) behavior, not a crash or a
  silently broken thumbnail.
- [ ] **Action:** Archive a History row (archive/dismiss affordance).
  **Expected outcome:** row disappears from the default History view;
  confirm via a filter/toggle that it's still reachable, not deleted.
- [ ] **Action:** With zero unopened-*Ready* captures, then submit and
  complete one capture to *Ready*.
  **Expected outcome:** menu-bar ready-indicator dot shows nothing
  beforehand, then appears as soon as the capture transitions to
  *Ready*.
- [ ] **Action:** Relaunch the app with existing *Ready*, unopened rows
  already in history.
  **Expected outcome:** no duplicate notifications fire for
  already-known ready rows on relaunch.
