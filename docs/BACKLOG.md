Added 2026-07-27 from the PR #26 code review (macOS 26 SpeechAnalyzer SIGTRAP fix). Findings #4/#5/#8 were applied in `111b7e7`, and #2 (locale released mid-session) plus the five-boolean/divergent-release-arithmetic finding were fixed in PR #26 itself — do not re-open either. The three below were deliberately deferred so each concurrency change gets its own verified state; verification here is a manual mic capture on macOS 26, not a test run, so batching them would cost regression attribution on a subsystem that (per the second item) has no automated coverage.

- **`LiveSpeechAnalyzerEngine` macOS 26 crash-fix has zero automated coverage** — the entire SIGTRAP-prevention wiring for macOS 26 lives in `apps/macos/Whistle/Services/SpeechAnalyzerTranscriber.swift`'s `LiveSpeechAnalyzerEngine`: the bounded `pendingBuffers` queue (capped at `maxPendingBuffers = 64`, drop-oldest via `removeFirst()`), the in-order drain into the analyzer, the `analyzerFormat` publish, the `AudioBufferConverter` convert-before-yield step, and the `AssetInventory.reserve`/`.release` locale handshake. Grepping `apps/macos/WhistleTests/` for `LiveSpeechAnalyzerEngine`, `pendingBuffers`, or `AssetInventory` returns nothing — every existing test injects `FakeSpeechAnalyzerEngine` (see TranscriptStitchingTests.swift) instead of exercising the real engine, and AudioBufferConverterTests.swift only exercises `AVAudioConverter` against a self-constructed Int16 format, never through the engine. The suite would pass with the whole engine reverted to the version that SIGTRAP'd in v1.0.9 — this is the exact hole the crash shipped through. Fix: extract the pending-buffer queue into a non-gated plain-Swift type and unit-test FIFO order/drop-oldest/drain directly; introduce an `AnalyzerInputSink` protocol (e.g. `func yield(_ input: AnalyzerInput)`) the engine writes to instead of touching `AsyncStream.Continuation` directly, so a fake sink can assert every yielded buffer has `format.commonFormat == .pcmFormatInt16`, runnable on any host without macOS 26 hardware; optionally wrap `AssetInventory`/`bestAvailableAudioFormat` behind an injectable protocol mirroring `SpeechAnalyzerResultsEngine` so the reserve/release state machine is fake-drivable too. Honest limit: this only prevents the *specific* regression (someone reverting the Int16 conversion), not the *class* of unknown-framework-precondition crashes, which are only findable at runtime — class-level prevention is the practice already recorded in `docs/solutions/runtime-errors/speechanalyzer-sigtrap-float32-audio-macos26.md`: treat "first run on a new OS" as a mandatory hardware-QA event.
- **Unstructured per-buffer Task in the mic tap has no ordering guarantee — now load-bearing, leading suspect for "transcription repeats itself"** — In `SpeechAnalyzerTranscriber.start()` (apps/macos/Whistle/Services/SpeechAnalyzerTranscriber.swift), the audio tap callback does `Task { await self.feed(buffer) }`, spawning one unstructured Task per buffer; Swift gives no FIFO guarantee across separately-created Tasks awaiting the same actor, so buffers can reach `LiveSpeechAnalyzerEngine.appendAudio` out of order. This line predates PR #26, but the diff made it load-bearing: pre-PR, `appendAudio` was a stateless `inputContinuation?.yield(...)` (see `git show 7e288edb`); it now feeds a stateful streaming `AVAudioConverter` (AudioBufferConverter.swift) whose comments assert an ordering invariant the Task-hop entry point doesn't enforce. `LegacySpeechTranscriber.start()` has the identical `Task { await self.feed(buffer) }` pattern. **First step: reproduce on the macOS 26 machine** to confirm or eliminate this as the cause of the known, already-established-as-our-bug "repeats itself" complaint — only change the hot path if it reproduces. If confirmed, fix by having the tap closure call `engine.appendAudio(buffer:)` synchronously (it's already non-async and `stateLock`-guarded, so ordering follows the tap's own callback order), or pump buffers through one long-lived Task consuming a single `AsyncStream<AVAudioPCMBuffer>`; decide whether to also fix `LegacySpeechTranscriber`.
- **SpeechAnalyzer setup has no timeout — a stall means a silently dead capture** — `LiveSpeechAnalyzerEngine.startAnalysis()`'s setup `Task` (apps/macos/Whistle/Services/SpeechAnalyzerTranscriber.swift) awaits `AssetInventory.reserve(locale:)` then `SpeechAnalyzer.bestAvailableAudioFormat(compatibleWith:)` with no time bound on either — both are asset/model-dependent (first-run download, disk, network) and can stall indefinitely. While stalled, `analyzerFormat` stays nil, so `appendAudio` ring-buffers into `pendingBuffers` (`maxPendingBuffers = 64`, ~5.5s) and then silently drops the oldest buffer forever via `removeFirst()` — no log, no counter. Meanwhile the mic tap stays live and `CaptureViewModel.beginRunningTranscription` has already set `isListening = true` with no pre-flight availability gate (that check, `checkAvailability`, only exists in onboarding's `PermissionStep`), so the UI shows a healthy-looking capture that produces an empty transcript with no surfaced error. Fix: race both awaits against a bounded `Task.sleep` (~10s) using `withThrowingTaskGroup` inside the setup `Task`; on timeout, yield `.error(...)` on `continuation`, call `continuation.finish()`, and go through the existing `releaseReservedLocale()` path so `SpeechAnalyzerTranscriber.handle`'s `.error` case tears the session down normally. Related, same review pass: the `pendingBuffers` drop-oldest path and `AudioBufferConverter`'s conversion-failure path (`yieldConvertedLocked`, which only `NSLog`s once via `didLogConversionFailure`) are both silent-degradation gaps worth closing alongside this — a stalled or degraded session currently leaves no trace in the UI or the unified log.
