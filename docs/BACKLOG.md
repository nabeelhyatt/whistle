- **`captures.retry` is not key-aware (canonical-accounts follow-up)** — `retry` (packages/backend/convex/captures.ts:119) deliberately preserves `workspaceId`/`sessionId`/`deepLink` for idempotency, but if the user swapped their Conductor API key to a different account since the original submit, the preserved workspace belongs to the *old* account: the retry's orphan-adoption/`sendMessage` calls 403/404 and the capture re-fails terminally. Fix: before rescheduling, probe `getWorkspaceStatus` with the current key (needs an action, so restructure `retry` to schedule a `pipeline.prepareRetry` internal action); on auth/404 clear `workspaceId`/`sessionId`/`deepLink` and remap `projectId` by name against the fresh project cache (or fail with guidance) so the retry re-creates under the current account. The new C2 project-visibility guard (pipeline.ts step 3·0) already covers the *fresh*-submit variant; this covers retry.
- **History-row Conductor provenance** — true "workspace not accessible from your Conductor app" is a client-side fact (which account the Mac Conductor app is signed into), invisible to the backend — the stored key can always open the workspace it created, so no backend probe detects the mismatch. Weak but cheap mitigation: on the History row detail, show provenance (key last-4 via `settings.get`, project `gitRemote`) and a "Can't find this workspace in Conductor?" help note explaining the two-account failure mode, shown after the user opens an `agentWorking`/`ready` row. Complements the C1 Settings project-set display shipped alongside the C2 guard.
