- **P1 — Unstructured per-buffer Task in the mic tap has no ordering guarantee — now load-bearing, leading suspect for "transcription repeats itself"** — In `SpeechAnalyzerTranscriber.start()` (apps/macos/Whistle/Services/SpeechAnalyzerTranscriber.swift), the audio tap callback does `Task { await self.feed(buffer) }`, spawning one unstructured Task per buffer; Swift gives no FIFO guarantee across separately-created Tasks awaiting the same actor, so buffers can reach `LiveSpeechAnalyzerEngine.appendAudio` out of order. This line predates PR #26, but the diff made it load-bearing: pre-PR, `appendAudio` was a stateless `inputContinuation?.yield(...)` (see `git show 7e288edb`); it now feeds a stateful streaming `AVAudioConverter` (AudioBufferConverter.swift) whose comments assert an ordering invariant the Task-hop entry point doesn't enforce. `LegacySpeechTranscriber.start()` has the identical `Task { await self.feed(buffer) }` pattern. **First step: reproduce on the macOS 26 machine** to confirm or eliminate this as the cause of the known, already-established-as-our-bug "repeats itself" complaint — only change the hot path if it reproduces. If confirmed, fix by having the tap closure call `engine.appendAudio(buffer:)` synchronously (it's already non-async and `stateLock`-guarded, so ordering follows the tap's own callback order), or pump buffers through one long-lived Task consuming a single `AsyncStream<AVAudioPCMBuffer>`; decide whether to also fix `LegacySpeechTranscriber`.
- **P1 — SpeechAnalyzer setup has no timeout — a stall means a silently dead capture** — `LiveSpeechAnalyzerEngine.startAnalysis()`'s setup `Task` (apps/macos/Whistle/Services/SpeechAnalyzerTranscriber.swift) awaits `AssetInventory.reserve(locale:)` then `SpeechAnalyzer.bestAvailableAudioFormat(compatibleWith:)` with no time bound on either — both are asset/model-dependent (first-run download, disk, network) and can stall indefinitely. While stalled, `analyzerFormat` stays nil, so `appendAudio` ring-buffers into `pendingBuffers` (`maxPendingBuffers = 64`, ~5.5s) and then silently drops the oldest buffer forever via `removeFirst()` — no log, no counter. Meanwhile the mic tap stays live and `CaptureViewModel.beginRunningTranscription` has already set `isListening = true` with no pre-flight availability gate (that check, `checkAvailability`, only exists in onboarding's `PermissionStep`), so the UI shows a healthy-looking capture that produces an empty transcript with no surfaced error. Fix: race both awaits against a bounded `Task.sleep` (~10s) using `withThrowingTaskGroup` inside the setup `Task`; on timeout, yield `.error(...)` on `continuation`, call `continuation.finish()`, and go through the existing `releaseReservedLocale()` path so `SpeechAnalyzerTranscriber.handle`'s `.error` case tears the session down normally. Related, same review pass: the `pendingBuffers` drop-oldest path and `AudioBufferConverter`'s conversion-failure path (`yieldConvertedLocked`, which only `NSLog`s once via `didLogConversionFailure`) are both silent-degradation gaps worth closing alongside this — a stalled or degraded session currently leaves no trace in the UI or the unified log.

- **P1 — Release the exact locale reservation variant returned by Speech** — `releaseReservedLocale()` currently enumerates `AssetInventory.reservedLocales` and matches BCP-47 identifier strings. Add a fakeable AssetInventory seam and cover variant plus concurrent-session cases.
